High-Level Design

Architecture overview — layer model, cross-dependencies, end-to-end sequences, decisions, and open questions.

1 · System Overview

The Role Widget Platform connects to each client's HR and business databases, normalises every employee into a role cluster (bucket), and serves them a personalised dashboard of decision widgets on day one. Widgets are shared templates with no client data; buckets, the knowledge graph, and all tenant content are private per client.

A reuse ladder (in-bucket → cross-bucket link → fork → generate) ensures no widget is created twice — the generator only runs when nothing in the library fits.

Users reach widgets through a growing question corpus, and their question sequences drive pre-loading of the next widget.

5 · Architecture Decisions

# Question Decision Effect
1 Widget storage model Shared widget templates; tenant data injected at render time Zero data leakage between tenants; single library to maintain
2 Bucket granularity Role cluster derived from JD similarity + org-level signals One bundle per bucket; employees with identical roles share cache
3 Reuse before generation Four-rung ladder enforced before generator is invoked Generation cost bounded; library grows via reuse not duplication
4 Cache layer Redis with RediSearch HNSW for semantic question index Sub-20 ms P99 on cache hit; vector ANN for bucket-first search
5 Access control granularity Widget-level can_access checked at serving time (LLD 10) Whole-widget blocking is default; scoped data option deferred — TBD
6 KG weight update cadence Feedback loop (LLD 9) batches novel-question signals; nightly weight rebuild KG stays fresh without per-question write amplification; lag ≤ 24 h TBD
7 Ingestion concurrency PeopleIngestionWorker paginates; fan-out BucketMatchJob per employee Parallelism bounded by worker pool size TBD; back-pressure via Kafka
8 New-bucket bootstrap NewBucketJob synthesises a starter bundle from nearest-neighbour buckets Day-one dashboard even for novel roles; quality improves as Feedback Loop runs

6 · Open Questions

Unresolved — needs a decision before implementation
  • First ERP / HRIS integration target — which system (SAP, Workday, or BambooHR) is the first integration target is not decided; shapes connector interface and SchemaDiscoveryWorker priority.
  • Field-level data scoping — whole-widget blocking is the current default in LLD 10; field-level scoping (restricting specific data columns rather than the whole widget) is confirmed as a requirement and must be designed into the DataResolver contract and cache key structure. Scoped results already use data_scope as a SQL predicate — the open work is expanding this to column-level filtering.
