LLD 01 — Ingestion / Role Widget Platform

LLD 01 — Ingestion

Turns a client ERP connection into normalised employees with JD chunks and hands each to bucket matching. Re-runs nightly and on webhook events.

Plain English

Connects to a client's HR or ERP system and syncs all employees into the platform. There are two sync modes: a full sync triggered when a new client first connects, and a nightly delta sync that re-processes only employees whose records have changed (new hire, role change, etc.). Job description edits are handled by webhook only — the nightly cron does not re-process JDs; the ERP pushes a webhook whenever a JD changes.

The core worker (PeopleIngestionWorker) pages through the ERP's employee API. For each employee it runs JDNormalizer, which extracts responsibility bullet points from the job description — falling back to a title + department template if no JD exists — and embeds them as vectors. In parallel, SchemaDiscoveryWorker reads the client's database structure and suggests which of their actual table names map to the generic aliases the platform's SQL templates use (e.g. their real table tbl_emp_current maps to the generic alias hr_employees).

At the end, a BucketMatchJob is queued for every employee whose JD hash changed. The system is idempotent — re-running the same sync produces the same result. A broken ERP connection only blocks that step; everything already synced is untouched.

3 · Components

POST /api/tenants/{tenant_id}/connect

Responsibility: Validate ERP type and credentials shape; store credentials in Secrets Manager; initialise tenant state rows.

Interface: POST /api/tenants/:tenant_id/connect → 202 Accepted | 400 | 409

Writes: tenant_erp_connections (status=pending), tenant_onboarding_state (stage=connecting)

Idempotency: Upsert on (tenant_id, erp_type); second call with same body is a no-op.

Failure handling: Invalid erp_type → 400. Duplicate active connection → 409. Secrets Manager write failure → 500, no DB row written.

ErpConnector.ping()

Responsibility: Lightweight read test against the ERP API to confirm credentials work before committing to a full sync.

Interface: ErpConnector.ping(tenant_id) → {ok: bool, error?: string}

Reads: Secrets Manager for credentials

Writes: tenant_erp_connections.status → running or error

Failure handling: Ping failure → set status=error, emit alert, stop pipeline. Retry not attempted automatically — admin must re-trigger.

PeopleIngestionWorker (async)

Responsibility: Paginate the ERP employee API (no page cap), normalise each employee record, upsert into tenant_users.

Interface: PeopleIngestionWorker.run(tenant_id, sync_type: 'full'|'delta') → void

Normalisation output per employee: {external_id, email, display_name, department, manager_id, raw_title, raw_jd_text, jd_source}

Reads: ERP employee API (paginated)

Writes: tenant_users upsert on (tenant_id, external_id)

Idempotency: Upsert; re-running the same page produces the same rows.

Failure handling: ERP rate limit → exponential backoff per tenant. Single page failure → retry that page only; other pages continue. Employee with no usable JD → pass to JD Normalizer with fallback signals.

JD Normalizer

Responsibility: Extract responsibility chunks from the best available JD text; embed chunks; persist to user_responsibilities; stamp jd_hash.

Fallback order: ERP JD text → job posting text → title + department template.

Interface: JDNormalizer.process(user_id, jd_text?, title, department) → {chunks: string[], jd_hash: string, jd_quality: 'ok'|'low'}

Reads: tenant_users

Writes: user_responsibilities (chunks + embeddings), tenant_users.jd_hash, tenant_users.jd_quality

Idempotency: Keyed on jd_hash; unchanged JD skips re-embedding.

Failure handling: LLM extraction failure → fall back to next source in order. All sources empty → bucket from title+department, flag jd_quality=low.

SchemaDiscoveryWorker (parallel)

Responsibility: Read information_schema on the client's read-only replica, embed table and column names, suggest mappings to generic aliases; persist after admin confirmation.

Interface: SchemaDiscoveryWorker.run(tenant_id) → {suggestions: MappingSuggestion[]}

Reads: Client DB information_schema (read-only replica)

Writes: tenant_schema_registry (partial — after admin confirm calls fn_register_table)

Runs: In parallel with PeopleIngestionWorker steps 3–4.

Failure handling: Read replica unreachable → log, skip, admin notified. Mapping suggestion errors do not block people sync.

BucketMatchJob fan-out

Responsibility: For every employee whose jd_hash changed since last sync, enqueue a BucketMatchJob.

Interface: fanOutBucketMatchJobs(tenant_id, changed_user_ids: string[]) → void

Reads: tenant_users.jd_hash diff

Writes: Job queue (Kafka topic / task queue)

Idempotency: Duplicate enqueue is safe — BucketMatchJob is idempotent.

Delta sync scheduler

Responsibility: Nightly cron that computes a content hash diff and skips unchanged employees to minimise LLM and DB writes.

Interface: Cron expression — DELTA_SYNC_CRON config.

Reads: tenant_users.jd_hash vs ERP current state

Writes: Enqueues PeopleIngestionWorker delta run per tenant

Failure handling: If ERP unreachable at cron time, retry window TBD; alert after N failures.

10 · Edge Cases & Open Questions

Edge Cases
  • Employee with completely empty JD and no department → bucketed from raw_title only, flagged jd_quality=low; bucket match quality degrades gracefully.
  • ERP pagination timeout mid-sync → retry that page only; employees already processed are not re-processed (jd_hash guard).
  • Duplicate external_id across sync runs (ERP reused an ID) → upsert overwrites the row; previous responsibility chunks are orphaned — open: should orphaned chunks be deleted or retained?
  • manager_id references a non-existent user → stored as-is; Access Guard resolves hierarchy lazily and handles missing nodes.
Open Questions
  • First ERP / HRIS integration target is undecided (SAP, Workday, BambooHR) — shapes connector interface priority.
  • Should orphaned user_responsibilities rows be deleted when a user's external_id is recycled by the ERP?
  • What is the retry window when the ERP is unreachable at scheduled cron time before alerting?
