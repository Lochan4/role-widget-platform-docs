LLD 03 — KG Selector / Role Widget Platform

LLD 03 — KG Selector

Walks the knowledge graph from an employee's responsibilities to the widgets that serve them, scores each path, and writes the personalised bundle. Every assignment is explainable as a KG path.

Plain English

Once an employee has a bucket, this builds their personal dashboard — the ordered list of widgets they should see. It walks the knowledge graph along the path: employee performs a responsibility → that responsibility is served by a widget, scoped only to widgets that belong to their bucket. It also adds "bucket-core" widgets — things the majority of bucket members use — even if this specific employee's JD didn't mention them, so everyone gets a complete baseline on day one.

Each widget gets a score based on knowledge graph edge weights and feedback signals from usage. Anything scoring above the inclusion threshold makes it into the bundle. A live / sample tag is applied to each widget: if the client has mapped their database tables, the widget shows real live data; otherwise it shows sample placeholder data until the mapping is done.

The bundle is written to the database atomically (delete + insert in one transaction) and simultaneously cached in Redis for fast dashboard delivery. A distributed lock prevents two concurrent builds for the same person from colliding.

After writing, it emits a BundleBuilt event listing any responsibilities that had no matching widget. That list goes straight to the Reuse Ladder (LLD 04) to close the gaps.

3 · Components

BundleBuildJob(user_id)

Responsibility: Orchestrate the full bundle build pipeline for a single user. Takes a distributed lock before starting to prevent concurrent builds for the same user.

Interface: BundleBuildJob.run(user_id) → void

Lock: Acquires lock:bundle-build:{user_id} (Redis NX, TTL=30s with heartbeat) before any work.

Idempotency: Repeated triggers collapse to one active build; lock owner completes the latest state, subsequent triggers find the lock held and exit.

Failure handling: Lock expire mid-job → idempotent writes make re-run safe (delete + insert in transaction).

KG Traversal

Responsibility: Walk: Employee → PERFORMS → Responsibility → SERVED_BY → Widget, restricted to Bucket -CONTAINS-> Widget for this user's bucket; status=active widgets only.

Interface: traverseKG(user_id, bucket_id) → {paths: KGPath[], uncovered: string[]}

Reads: kg_nodes, kg_edges, user_responsibilities, user_bucket_map

Writes: None

Idempotency: Read-only traversal.

Bucket-Core Widget Adder

Responsibility: Add widgets linked to responsibilities that the majority of bucket members share, even if this specific user's JD didn't mention them. Ensures new members get a full baseline bundle immediately.

Interface: addCoreWidgets(user_id, bucket_id, traversalPaths) → KGPath[]

Reads: kg_edges (CONTAINS edges with core_widget flag), user_bucket_map

Writes: None (returns augmented path list)

Path Scorer

Responsibility: Score each widget by summing across all paths that lead to it.

Formula: score = Σ(PERFORMS_weight × SERVED_BY_weight) + core_widget_boost − feedback_penalty

Interface: scorePaths(paths: KGPath[], feedback: FeedbackMap) → WidgetScore[]

Reads: kg_edges.weight, feedback data from LLD 9

Writes: None

Inclusion Filter

Responsibility: Keep every widget whose score clears WIDGET_INCLUSION_THRESHOLD. No top-N cap — the threshold is the only gate.

Interface: filterWidgets(scores: WidgetScore[]) → WidgetScore[]

Reads: Config threshold

Writes: None

Live/Sample Tagger

Responsibility: For each widget in the filtered set, call fn_live_widgets(tenant_id) to determine whether the widget has live data or will render in sample mode for this tenant.

Interface: tagLiveSample(widgets: WidgetScore[], tenant_id) → TaggedWidget[]

Reads: tenant_schema_registry via fn_live_widgets

Writes: None

Bundle Writer

Responsibility: Write the final bundle atomically. Delete existing rows for user + insert new rows, store the KG explanation path per widget, refresh Redis cache.

Interface: writeBundle(user_id, widgets: TaggedWidget[], paths: KGPath[]) → void

Reads: None

Writes: user_widget_bundle (delete + insert in one transaction), bundle:{user_id} in Redis (SET, TTL=86400s)

Idempotency: Delete + insert inside a transaction; safe to re-run.

Failure handling: DB transaction failure → Redis not updated; stale Redis entry expires within TTL; next build corrects both.

BundleBuilt Emitter

Responsibility: After bundle write, emit BundleBuilt(user_id, uncovered_responsibilities) to trigger gap analysis in LLD 4.

Interface: emitBundleBuilt(user_id, uncovered: string[]) → void

Reads: None

Writes: Event bus / Kafka topic

Idempotency: Duplicate emits safe — LLD 4 deduplicates by responsibility.

9 · Edge Cases & Open Questions

Edge Cases
  • User in no bucket (still unbucketed) → write empty bundle + flag "being set up"; show holding card on dashboard.
  • All widgets in sample mode (no live data sources for tenant) → bundle is written with all entries tagged sample; user sees widgets with placeholder data.
  • Lock expired mid-job → bundle delete+insert is transactional; a re-run produces the correct final state. The Redis entry may briefly be stale but expires within TTL.
  • Responsibility with no widgets in any bucket → surfaces in uncovered_responsibilities sent to LLD 4; does not block the bundle write.
Open Questions
  • Should WIDGET_INCLUSION_THRESHOLD be global or per-bucket? Per-bucket allows tuning but increases config surface.
  • How should the bundle handle a widget that was in the previous bundle but now scores below threshold? Silent removal or a grace period?
