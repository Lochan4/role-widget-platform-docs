LLD 04 — Reuse Ladder

Closes coverage gaps by linking or forking existing widgets before ever calling the generator. Generation is the last rung, not the first.

Plain English

When a responsibility has no widget, it becomes a gap. Gaps accumulate silently until enough bucket members are affected (or an admin forces it). Once a gap is active, this component tries to close it as cheaply as possible by climbing four rungs in order — the AI generator is only called on the fourth rung:

  1. Re-weight — is there already a widget in this bucket that could serve this responsibility if we lower the scoring threshold slightly? If yes, adjust the knowledge graph edge weight. Zero new code, zero cost.
  2. Cross-bucket link — is there a widget in a different bucket that semantically matches and whose data requirements the client has already mapped? If yes, add a link edge. No new widget created.
  3. Fork / adapt — is there a close match that just needs different KPIs, filters, or data grain? One small LLM call produces a spec override. The fork inherits the parent's question corpus and is copy-on-write.
  4. Generate — nothing fits. Write the gap to the generation queue for LLD 05. This is the expensive path.

Each successful close triggers a bundle rebuild for every member of the affected bucket and a Redis version bump. In practice most gaps close at rung 2 or 3. Rung 4 is deliberately hard to reach — the ladder is the system's primary cost-control mechanism.

3 · Components

Gap Aggregator

Responsibility: Collect uncovered responsibilities per bucket. A gap activates when member_count ≥ GAP_ACT_MEMBER_THRESHOLD or admin-flagged. Personal gaps (single-user unusual task) → personal widget link, no bucket change.

Interface: aggregateGap(responsibility_id, bucket_id, user_id) → GapRecord

Reads: bucket_coverage_gaps, user_bucket_map

Writes: bucket_coverage_gaps (upsert, increment member_count)

Idempotency: Upsert on (responsibility_id, bucket_id); safe to call multiple times for the same user.

Rung 1 — In-Bucket Re-weight

Responsibility: Check KG for widgets already in this bucket that could serve the responsibility at a lower inclusion threshold. If found, re-weight the SERVED_BY edge rather than adding anything new.

Interface: tryReweight(responsibility_id, bucket_id) → {hit: bool, edge_id?: string}

Reads: Redis bucket:{id}:v (version lookup); kg_edges

Writes: kg_edges.weight (update on hit)

Failure handling: No hit → pass to Rung 2.

Rung 2 — Cross-Bucket Link

Responsibility: ANN search over all active widget embeddings and their question corpora. Matching criteria: embedding or question vector close to responsibility vector, data requirements mappable for this tenant, no negative rating from similar buckets. On match: insert Bucket -CONTAINS-> Widget edge with mode=linked.

Interface: tryLink(responsibility_id, bucket_id, tenant_id) → {hit: bool, widget_id?: string}

Reads: pgvector ANN on widget embeddings + question embeddings; tenant_schema_registry for mapping check; widget_access for negative rating check

Writes: kg_edges (CONTAINS, mode=linked) on hit

Failure handling: No hit → pass to Rung 3.

Rung 3 — Fork / Adapt

Responsibility: Close match exists but needs different KPIs, filters, grain, or threshold. One small LLM call to produce spec overrides. Result: copy-on-write fork with parent_widget_id + spec_overrides. Fork inherits parent question corpus by reference. Parent spec change flags fork for review.

Interface: tryFork(responsibility_id, candidate_widget_id, bucket_id) → {hit: bool, fork_widget_id?: string}

Reads: Parent widget spec; responsibility description

Writes: widgets (fork row), kg_edges (CONTAINS for fork, parent_widget_id back-reference)

Failure handling: LLM call failure → retry once; if still failing, escalate to Rung 4 (generate).

Rung 4 — Generate

Responsibility: No usable match found on any rung. Write the gap to generation_queue for LLD 5.

Interface: escalateToGeneration(gap_id) → void

Writes: generation_queue (insert with priority score)

Idempotency: Upsert on gap_id; duplicate escalations are no-ops.

KG Edge Writer

Responsibility: Insert CONTAINS + SERVED_BY edges for linked or forked widgets; bump bucket_version; invalidate bucket:{id}:* in Redis; enqueue BundleBuildJob for all bucket members.

Interface: writeKGEdges(bucket_id, widget_id, edge_type, mode) → void

Reads: None

Writes: kg_edges, buckets.version, Redis bucket:{id}:v (INCR), Redis bucket:{id}:{v}:widgets (invalidate), job queue (BundleBuildJob per member)

Idempotency: Upsert on (bucket_id, widget_id, edge_type).

Gap Closer

Responsibility: After any rung succeeds, mark the gap as resolved with the method used.

Interface: closeGap(gap_id, resolved_by: 'link'|'fork'|'generate') → void

Writes: bucket_coverage_gaps.resolved_by, bucket_coverage_gaps.status = closed

10 · Edge Cases & Open Questions

Edge Cases
  • Personal gap (single user, unusual task) → bypass bucket accumulation; create a personal widget link directly without changing bucket state.
  • Rung 3 fork produces a widget nearly identical to existing library entry → validator in LLD 5 pre-dedupe step will catch near-duplicates if the fork is later regenerated; Rung 3 should re-check ANN before committing fork.
  • Bucket version races: two concurrent Rung 2 writes for the same bucket → both upsert on (bucket_id, widget_id, edge_type); last writer wins, bucket version is correct.
Open Questions
  • Fork sprawl risk — forks should require a real spec difference; need a process to detect and merge forks back when the difference disappears (e.g., parent spec update narrows the gap).
  • When a gap is closed by Rung 2 (cross-bucket link), should the linked widget appear on the bucket dashboard immediately, or only after the next bundle rebuild cycle?
  • Should personal gaps (single user) ever escalate to bucket-level gaps if the same personal task appears for multiple unrelated users over time?
