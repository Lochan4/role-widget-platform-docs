LLD 05 — Generator

When a gap falls through the reuse ladder, one generator run produces the entire family of widgets needed for that responsibility, each deduplicated against the library. Generation is the last rung, not the first.

Plain English

When the Reuse Ladder exhausts all four rungs, this creates new widgets from scratch. One generation run produces an entire family — all the widgets a responsibility needs — in a seven-step pipeline:

  1. Decompose — one LLM call turns the responsibility text into a list of decision intents (e.g. "track headcount vs plan", "spot attrition risk").
  2. Map to forms — each intent is mapped to one or more of the seven fixed widget forms: KPI, trend, comparison, breakdown, alert, forecast, action.
  3. Pre-dedupe — before generating anything, a semantic search checks each intent-form pair against the existing widget library. Close matches go back to rung 2 (link). Only genuinely novel pairs proceed.
  4. Batch spec generation — one batched LLM call (with examples of well-rated widgets of the same form type as few-shot guidance) produces full specs, including SQL query templates and seed questions.
  5. Validate — schema check, verify SQL templates only use known generic table aliases, reject near-duplicates within the batch.
  6. Feasibility — check which clients have the required data sources mapped. Clients without the data see sample mode; the widget is still created.
  7. Review queue — the entire widget family goes to an admin for approval. On approval: widgets written to the library, knowledge graph edges created, questions embedded and indexed, cache warmed.

There is a token budget per client per day and a global daily budget — the system never generates beyond these limits. The same responsibility triggered from multiple clients within a time window is coalesced into one generation run, so the cost and output are shared.

3 · Components

Gap Lifecycle Manager

Responsibility: Manage the gap state machine (open → accumulating → ready → generating → in_review → closed). Coalesce the same responsibility across buckets/tenants within the coalescing window before starting a job. Re-run the reuse ladder before starting (library may have changed since the gap was queued).

Interface: GapLifecycleManager.advance(gap_id) → void

Reads: generation_queue, bucket_coverage_gaps

Writes: generation_queue.status, bucket_coverage_gaps.status

Idempotency: State transitions are guarded; advancing an already-advanced gap is a no-op.

Priority Queue Worker

Responsibility: Pull ready gaps from generation_queue ordered by priority score (employees affected × question frequency × recency × bucket-empty flag). Budget-aware: checks per-tenant daily token budget and global daily token budget before starting a run.

Interface: PriorityQueueWorker.poll() → GenerationJob | null

Reads: generation_queue, token budget counters (Redis or DB)

Writes: generation_queue.status = generating

Failure handling: Budget exhausted → job stays in ready state until next budget window. Worker crash mid-job → gap reverts to ready (heartbeat + timeout).

Responsibility Lock

Responsibility: One generation per responsibility canonical ID at a time. Prevents duplicate runs for the same responsibility triggered from different buckets during the coalescing window.

Interface: acquireLock(responsibility_canonical_id) → bool

Writes: Redis SETNX genlock:{responsibility_canonical_id} (TTL = GENERATION_LOCK_TTL_SECONDS)

Step 1 — Decompose Responsibility

Responsibility: One LLM call: responsibility text + bucket name + sample JD lines → list of decision intents.

Interface: decomposeResponsibility(responsibility_text, bucket_name, jd_samples[]) → Intent[]

Writes: generation_runs (step 1 output)

Failure handling: LLM failure → retry with backoff; after max retries, gap reverts to ready.

Step 2 — Map Intents to Widget Forms

Responsibility: Map each intent to one or more widget forms from the fixed catalogue: kpi, trend, comparison, breakdown, alert, forecast, action. One intent → multiple forms permitted.

Interface: mapToForms(intents: Intent[]) → IntentFormPair[]

Writes: generation_runs (step 2 output)

Step 3 — Pre-Dedupe

Responsibility: Embed a one-line description for each (intent, form) pair; ANN against the widget library. Close match → back to LLD 4 Rung 2 (link); only unmatched pairs proceed to generation.

Interface: preDedupeFilter(pairs: IntentFormPair[]) → {proceed: IntentFormPair[], linked: IntentFormPair[]}

Reads: pgvector ANN on widget embeddings

Writes: None (links handled by LLD 4 Rung 2 callback)

Step 4 — Batch Spec Generation

Responsibility: One batched LLM call (few-shot with well-rated widgets of the same forms) to produce full specs for all unmatched pairs.

Output per widget: {title, description, purpose, form, spec, data_query_template, data_requirements[], responsibility_ids[], intent, seed_questions[]}

Interface: batchGenerate(pairs: IntentFormPair[], fewShotExamples[]) → WidgetDraft[]

Writes: generation_runs (step 4 output — raw LLM response)

Cost controls: One decomposition call + one batched spec call per responsibility. Results cached by responsibility canonical embedding — retry or similar gap reuses the output.

Step 5 — Validator

Responsibility: JSON schema check; data_query_template must parse and use only known generic aliases; reject near-duplicates within the batch.

Interface: validateDrafts(drafts: WidgetDraft[]) → {valid: WidgetDraft[], rejected: WidgetDraft[]}

Reads: tenant_schema_registry generic aliases

Failure handling: Rejected widgets are logged; the valid portion of the batch continues. If all rejected, gap reverts to ready for re-generation.

Step 6 — Feasibility Checker

Responsibility: For each valid widget, determine which tenants have data_requirements mapped: available / partial / unavailable. Unavailable widgets are still stored — they surface in sample mode for tenants without the data.

Interface: checkFeasibility(drafts: WidgetDraft[], tenant_id) → FeasibilityTaggedDraft[]

Reads: tenant_schema_registry

Writes: Feasibility tag on each draft (not persisted until approval)

Step 7 — Review Queue Publisher

Responsibility: Group widgets as a family; push to review queue for admin approval. On approval: insert into widgets, write KG edges, embed widget + questions, enqueue CacheWarmJob(bucket_id). While in review: affected employees see closest linked widgets in sample mode, or "being set up" card.

Interface: publishToReviewQueue(family: FeasibilityTaggedDraft[], generation_run_id) → void

Reads: None

Writes: Review queue record; on approval: widgets, widget_questions, widget_access, kg_edges, CacheWarmJob enqueue, generation_queue.status = closed

10 · Edge Cases & Open Questions

Edge Cases
  • Step 3 pre-dedupe routes most pairs back to LLD 4 Rung 2 — generator may produce zero new widgets for a run; gap is closed with resolved_by=link, not generate.
  • All generated drafts fail Step 5 validation → entire batch rejected; gap reverts to ready; failure logged for LLM prompt tuning.
  • Token budget exhausted mid-batch → completed drafts saved; remaining pairs requeued for next budget window.
  • Admin rejects entire widget family → gap returns to generating; re-generation uses a different few-shot example set to avoid repeating the same output.
  • Same responsibility reaches ready simultaneously from two tenants during the coalescing window → coalesced into a single generation run; resulting widgets are feasibility-tagged per tenant.
Open Questions
  • How many few-shot examples should Step 4 use, and how should they be selected (highest-rated of same form, or most semantically similar responsibility)?
  • Should generation results (Step 4 output) be cached by responsibility canonical embedding? If so, for how long — the library could change and make the cached output stale.
  • Is one admin approval per widget family the right granularity, or should individual widgets within a family be approvable independently?
