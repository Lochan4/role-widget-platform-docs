LLD 06 — Question Router

Matches a user's natural-language question to the right widget(s) using bucket-first vector + keyword search, boosts by session transition probability, and returns a grounded LLM answer.

Plain English

The employee-facing intelligence layer. An employee types a question; this returns a grounded answer using live data from that client's database. The flow on a cache miss:

  1. Normalise the question text and compute a deterministic cache key.
  2. Search the Redis semantic question index for matching questions in the employee's bucket — filtered by their access level before ranking.
  3. Apply a session boost: if they just asked question A, and question B typically follows A in session history, boost B's score.
  4. If nothing clears the match threshold, widen — first to secondary buckets, then to the global widget library. A global library hit is logged as a gap signal and sent to the Reuse Ladder (LLD 04), since this responsibility probably needs its own widget in this bucket.
  5. Access Guard is checked again before any data is passed to the LLM.
  6. The LLM composes a grounded answer using widget data and the matched questions as context.
  7. Answer is cached in Redis and logged.
  8. The next-question predictor suggests follow-ups from session history and pre-warms those widgets' data in Redis.

Every unanswered question is flagged as novel and sent to the Feedback Loop (LLD 09) for cluster analysis — if enough different employees ask similar unmatched questions, a new widget will eventually be generated to answer them.

3 · Components

Normalizer + Hasher

Responsibility: Normalise text (lowercase, strip punctuation), compute cache key hash = sha256(normalized_text + bucket_id + access_scope); check rag:{hash}:{data_v} in Redis.

Interface: normalizeAndHash(text, bucket_id, access_scope) → {normalized: string, hash: string, cacheHit?: AnswerJSON}

Reads: Redis rag:{hash}:{data_v}

Writes: None

Idempotency: Deterministic hash; same question from same user always produces the same key.

Bucket-First Search

Responsibility: Vector + keyword search over questions linked to widgets in the user's bucket, served from the qidx:bucket RediSearch HNSW index. Candidates filtered by Access Guard (LLD 10) before ranking. Accept every widget whose best question match clears ROUTING_THRESHOLD.

Interface: bucketFirstSearch(normalized_text, bucket_id, user_id) → Candidate[]

Reads: Redis qidx:bucket (RediSearch HNSW); LLD 10 can_access

Writes: None

Failure handling: RediSearch index miss (new bucket, empty) → widening logic handles.

Session Boost

Responsibility: If the session has a previous question, add transition probability P(candidate | previous_question) from question_transitions to each candidate's score.

Interface: applySessionBoost(candidates: Candidate[], session_id) → Candidate[]

Reads: question_transitions (by previous question ID → candidate question ID)

Writes: None

Failure handling: No previous question in session → no boost applied; candidates returned with base scores.

Widening Logic

Responsibility: If nothing clears ROUTING_THRESHOLD after bucket-first + session boost: widen to secondary buckets (including inferred from LLD 11) → then global library. A global hit records a gap candidate for LLD 4. Access filter applied at every widening level.

Interface: widenSearch(normalized_text, user_id, failedBucketId) → {candidates: Candidate[], globalHit: bool}

Reads: Redis secondary bucket indexes, global qidx; LLD 10 access filter

Writes: Gap candidate signal → LLD 4 (async, non-blocking)

Answer Generator (LLM)

Responsibility: Receive widget data + matched questions; produce a grounded answer. Access Guard runs again before passing data to the LLM (double-check in case access changed since initial filter).

Interface: generateAnswer(widget_data, matched_questions, user_id) → AnswerJSON

Reads: Widget data from LLD 8 (wdata:{widget_id}:{tenant_id}:{scope}); LLD 10 access re-check

Writes: Redis rag:{hash}:{data_v} (SET with TTL = RAG_CACHE_TTL_SECONDS); rag_answers table

Failure handling: LLM failure → return error response; do not cache failures.

Next-Question Predictor

Responsibility: From question_transitions, take likely next questions above TRANSITION_PROBABILITY_FLOOR; return as suggested follow-ups. Pre-warm their widgets' data in Redis by enqueuing lightweight data refresh jobs.

Interface: predictNextQuestions(matched_question_id, bucket_id) → SuggestedQuestion[]

Reads: question_transitions

Writes: Enqueue data pre-warm for suggested widget IDs (async)

Logger

Responsibility: Write question_log row for every request: {user_id, session_id, seq, text, matched_question_id or null, widget_id, scores}. Unmatched text is flagged as a novel question for LLD 9.

Interface: logQuestion(request, result) → void

Writes: question_log; novel question signal → LLD 9 (async)

Failure handling: Log write failure is non-blocking; answer is returned regardless.

Transition Learner (nightly job)

Responsibility: Read consecutive question pairs per session, map to canonical question IDs, update pair counts in question_transitions. Apply smoothing and time decay. Novel questions join the transition graph once promoted by LLD 9.

Interface: TransitionLearner.run(date) → void

Reads: question_log

Writes: question_transitions (upsert counts + decayed weights)

Idempotency: Re-running for the same date is safe (upsert on (q_from, q_to, bucket_id)).

9 · Edge Cases & Open Questions

Edge Cases
  • No widgets in bucket (new tenant, empty bucket) → bucket-first search returns zero candidates; widening goes straight to global search. If still no match, return "no answer available yet" with "being set up" message.
  • Session with no previous question → no boost applied; candidates ranked purely by vector + keyword score.
  • Multiple widgets tie on score above threshold → return all of them; employee sees all matched widgets, not just the top one.
  • Question that matches only access-denied widgets → do not surface those widgets; reply "restricted for your role" and offer allowed alternatives if any exist above threshold.
  • Cache hit but data version has changed (data_v differs) → miss; new answer generated with fresh data; old key orphaned until TTL expiry.
Open Questions
  • How should access_scope be included in the cache key hash — as a stable string representation of the user's current permission set? This must not change silently when permissions change.
  • Should transition probability decay be applied per bucket (heavier decay on low-activity buckets) or globally?
  • When widening to the global library hits a match, should that result always record a gap candidate for LLD 4, or only when the match is below a quality threshold?
