LLD 07 — Redis Cache

Holds each bucket's widgets and question index as the first lookup layer; Postgres is the source of truth behind it. Every key is versioned so invalidation is exact and stale reads cannot happen.

Plain English

The speed layer. Everything the serving path touches lives here first — Postgres is the fallback, not the first call. There are nine key families; the important ones:

  • bundle:{user_id} — the employee's ordered widget list. Rebuilt whenever their bucket, access level, or a widget changes.
  • bucket:{id}:v + bucket:{id}:{v}:widgets — versioned widget set per bucket. A version bump instantly makes the old set stale; there is no window where a stale read can happen.
  • qidx:bucket — a RediSearch HNSW vector index of all questions, tagged by bucket and widget. This is what powers the semantic search in LLD 06.
  • wdata:{widget_id}:{tenant_id}:{scope} — cached query results per widget per client. Deleted the moment the source data changes (via Kafka CDC).
  • rag:{hash}:{data_v}:{scope} — cached LLM answers. The access scope is part of the key so user A's filtered answer is never served to user B with different permissions.
  • wacl:* + uacl:* — widget access metadata and user access profiles. Pinned — never evicted. Evicting these would cause wrong access decisions; any eviction triggers an immediate alert.

The eviction policy uses two tiers: data and answer keys use LRU eviction (they can be regenerated). Bucket, index, and access keys are pinned with no eviction policy — these must always be in memory.

3 · Components

CacheWarmJob(bucket_id)

Responsibility: On bucket change, widget activation, or new tenant onboarding: load the bucket's widgets as a scored set, upsert questions into the RediSearch index, warm the first page of each live widget's data per tenant, and warm predicted next-question widgets per session (drawn from LLD 6 transition graph).

Interface: CacheWarmJob.run(bucket_id, tenant_id?) → void

Reads: widgets, questions, widget_data_sources, LLD 6 session transition graph

Writes: bucket:{id}:v, bucket:{id}:{v}:widgets, qidx:bucket upserts, wdata:* first-page warm

Concurrency: Parallelism capped by CACHE_WARM_CONCURRENCY; each bucket warm is idempotent.

Failure handling: Partial warm is acceptable — any miss falls to Postgres via MissTracker; job logs per-bucket success/failure.

qidx:bucket — RediSearch HNSW Index

Responsibility: Stores all question vectors and text with bucket_id and widget_id tags. KNN search filters on @bucket_id:{id}. Linked widget questions carry every bucket they belong to — linking adds a tag, not a copy of the document.

Index fields: vector VECTOR HNSW, text TEXT, bucket_id TAG, widget_id TAG, min_level NUMERIC

Used by: LLD 6 (question routing KNN), LLD 10 (level filtering applied in search query)

Invalidation: Upsert or delete per question; no TTL — pinned key family.

Versioned Key Manager

Responsibility: Every membership or widget change increments bucket:{id}:v. Readers resolve the current version first, then read bucket:{id}:{v}:widgets. Old versioned keys age out by TTL (86400s). Prevents the race where a reader repopulates a key during invalidation.

Protocol: GET bucket:{id}:v → v; ZRANGEBYSCORE bucket:{id}:{v}:widgets …. Writers bump version atomically via INCR bucket:{id}:v before writing new key.

Failure handling: If version key is missing (e.g., after Redis restart), reader treats as miss → Postgres fallback → CacheWarmJob re-queued.

Bundle Writer

Responsibility: Writes bundle:{user_id} as JSON after LLD 3 BundleBuildJob completes. Uses delete-then-set pattern (not GETSET) to avoid returning a stale bundle during the brief gap — callers that miss fall back to a synchronous rebuild.

Interface: writeBundle(user_id, payload: BundleJSON) → void

TTL: BUNDLE_TTL_SECONDS TBD

Invalidation: Bundle rebuild triggered by bucket change, access change, widget deprecation, or LLD 11 secondary-bucket assignment.

LRU Eviction Policy

Responsibility: Data and answer keys (wdata:*, rag:*) live on the LRU eviction tier. Bucket and index keys (bucket:*, qidx:*, wacl:*, uacl:*) are pinned and must not be evicted.

Implementation: Two logical Redis tiers (can be two databases or separate clusters): LRU tier has maxmemory-policy allkeys-lru; pinned tier has maxmemory-policy noeviction. If unified cluster is used, pinned keys must have no TTL and be monitored separately.

Alert condition: Eviction of any key in the pinned family → page immediately.

Miss Tracker

Responsibility: Any cache miss falls back to Postgres, fills the key, and records the miss metric per key family. High miss rate on bucket:* means CacheWarmJob is lagging; high miss rate on wdata:* is expected on cold tenants.

Interface: MissTracker.record(key_family: string, key: string) → void

Emits: cache.miss metric tagged by key_family; alert threshold per family is configurable.

10 · Edge Cases & Open Questions

Edge Cases
  • Redis restart — all keys lost; CacheWarmJob replays for all active buckets; RediSearch index is rebuilt from Postgres; reads fall to Postgres during warm-up (expected elevated miss rate).
  • Eviction of a pinned key under extreme memory pressure — must alert immediately; no silent stale reads; operator must either expand memory or reduce LRU tier usage.
  • Bucket with 1000+ widgets — sorted set is fine at that cardinality but bundle delivery to the client needs pagination; the full sorted set is not sent raw to the browser.
  • CacheWarmJob lag on a large tenant with many buckets — warm concurrency capped; newly onboarded tenant sees elevated misses until warm completes; MissTracker alert fires if lag exceeds threshold.
Open Questions
  • Single Redis cluster vs. two tiers (LRU + noeviction) — operational complexity trade-off; one cluster is simpler but pinned-key eviction risk is higher under memory pressure.
  • Should rag:* keys include the access scope in the cache key to prevent cross-user answer leakage, or is data_version granularity sufficient? (LLD 10 notes scope in key.)
  • RediSearch index rebuild time on restart for a large corpus — is a warm-standby replica needed to avoid routing downtime?
