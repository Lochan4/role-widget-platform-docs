LLD 08 — Data Resolver

Resolves widget SQL templates to tenant-specific queries via the schema registry, and serves live widget data — switching a widget from sample to live the moment all its tables are mapped and validated.

Plain English

Bridges the gap between the platform's generic widget SQL templates and each client's actual database. Widget templates use placeholders like {{hr_employees}}. This layer takes the admin's confirmed mapping of that placeholder to their real table name and renders actual SQL.

Before any query ever runs, it runs EXPLAIN on the client's read-only replica — this validates that all column names and tables exist without executing the query or touching any rows. Only after EXPLAIN passes is the query marked verified and the widget flips from sample mode to live. LLM output from generation is never executed as SQL at request time — all queries come from reviewed templates. Every query runs under a per-client credential scoped only to that client's mapped tables.

Live query results are cached in Redis by refresh class (realtime, hourly, or daily). When the client's underlying data changes — detected via Kafka change-data-capture events from Debezium — the corresponding cache keys are deleted immediately. Bulk data loads are debounced to collapse many rapid events into a single invalidation.

3 · Components

Schema Registration Flow

Responsibility: Triggered by LLD 1 step 5 or admin UI. Accepts the admin's confirmation of generic_name → actual_name, writes the registry row, invalidates pre-rendered SQL for every affected widget, then fans out QueryRenderJob for each.

Steps:

  1. Admin confirms mapping in UI.
  2. fn_register_table upserts tenant_schema_registry (verified=false), deletes affected tenant_widget_queries rows.
  3. Fan out QueryRenderJob(tenant_id, widget_id) for every widget that uses the alias.
  4. EXPLAIN validator runs on read-only replica.
  5. Pass → verified=true; fail → error stored, admin notified.
  6. fn_live_widgets(tenant_id) recomputed; data_mode_version bumped; bundles re-tagged (live/sample) without full rebuild.
fn_register_table(tenant_id, generic_name, actual_name, db_schema)

Responsibility: Upserts into tenant_schema_registry with verified=false. Deletes all tenant_widget_queries rows for this tenant that reference the alias so they are re-rendered from scratch.

Interface: fn_register_table(tenant_id, generic_name, actual_name, db_schema) → void (Postgres function, already in schema.sql)

Writes: tenant_schema_registry (upsert), tenant_widget_queries (delete invalidated rows)

Idempotency: Upsert on (tenant_id, generic_name); re-registering same actual_name is a no-op beyond the delete.

QueryRenderJob(tenant_id, widget_id)

Responsibility: Reads data_query_template from the widgets table, substitutes all {{alias}} placeholders with the tenant's confirmed actual_name values from the registry, and stores the result in tenant_widget_queries.resolved_sql.

Interface: QueryRenderJob.run(tenant_id, widget_id) → void

Reads: widgets.data_query_template, tenant_schema_registry (confirmed mappings only)

Writes: tenant_widget_queries (upsert resolved_sql)

Failure handling: Missing mapping for an alias → job fails cleanly; widget stays in sample mode; admin notified with the unresolved alias name.

EXPLAIN Validator

Responsibility: Runs EXPLAIN (never EXECUTE) on the resolved SQL against the tenant's read-only replica under the tenant's read-only DB role. Validates column names and table existence. Reports the exact failing column or table in the error.

Interface: ExplainValidator.validate(tenant_id, widget_id, resolved_sql) → {ok: bool, error?: string}

Timeout: EXPLAIN_VALIDATION_TIMEOUT_MS TBD

Writes on pass: tenant_schema_registry.verified=true for affected aliases

Writes on fail: tenant_widget_queries.validation_error stored; widget remains sample

fn_live_widgets(tenant_id)

Responsibility: Returns the set of widget slugs for which all required data sources have a verified mapping in tenant_schema_registry. Called after each successful EXPLAIN validation to recompute the live set without a full bundle rebuild.

Interface: fn_live_widgets(tenant_id) → widget_slug[] (Postgres function, already in schema.sql)

Reads: widget_data_sources, tenant_schema_registry

Effect: Bundles re-tag widgets live/sample; data_mode_version bumped so stale bundles are detected.

GET /api/widgets/{id}/data — Data Fetch Handler

Responsibility: Authoritative data endpoint. Checks wdata:{widget_id}:{tenant_id}:{scope} in Redis first. On hit, returns immediately. On miss: run resolved_sql on read-only replica under tenant's DB role (statement_timeout + row_limit enforced); cache result with TTL per refresh class; return rows.

Sample mode: Widget without a verified resolved_sql returns the bundled sample dataset instead of executing SQL.

Security: SQL comes only from reviewed templates with validated identifiers. Never from LLM output at request time. Every query runs under a per-tenant credential with access only to that tenant's mapped tables.

Failure handling: Statement timeout → return error + serve stale cache if available. Row limit exceeded → return truncated rows + warning header.

CacheInvalidationConsumer

Responsibility: Consumes Debezium → Kafka topic tenant.{tenant_id}.changes. Maps changed table → alias → widgets that need that alias. Deletes wdata:* keys and dependent rag:* keys for each affected widget/tenant pair. Debounces bulk loads into one invalidation per window.

Interface: Kafka consumer group; processes messages in order per tenant partition.

Debounce: CDC_DEBOUNCE_WINDOW_MS TBD — multiple CDC events for the same table within the window collapse to one invalidation.

Failure handling: Consumer lag monitored; if lag exceeds threshold, stale data risk must be alerted. Dead-letter queue for unparseable events.

8 · Security Note

Security invariants
  • SQL comes only from reviewed templates with validated identifiers. LLM output is never executed as SQL at request time.
  • Every query runs under a per-tenant DB credential that is read-only and scoped to that tenant's mapped tables only.
  • EXPLAIN is run before any execution; a template that fails EXPLAIN can never reach execution.
  • The data_scope filter (self/team/department/company) is applied as a mandatory SQL predicate injected by LLD 10, never in the UI.

10 · Edge Cases & Open Questions

Edge Cases
  • Tenant maps alias to a non-existent table — EXPLAIN fails, widget stays in sample mode; admin receives exact error (table not found).
  • Bulk data load triggers many CDC events in rapid succession — debounce collapses them; brief window of stale cache acceptable per refresh class contract.
  • Resolved SQL becomes invalid after tenant DB schema change (column renamed) — EXPLAIN fails on next access; widget falls back to sample; admin notified to re-map.
  • Two widgets sharing the same alias that one tenant has not yet mapped — only the unmapped widget stays in sample; the other goes live independently.
Open Questions
  • Should EXPLAIN validation run periodically (e.g., nightly) to catch silent tenant schema drift, or only on mapping change and access?
  • What is the observable behaviour when a widget is mid-transition from sample to live during an active user session?
  • Kafka consumer group per tenant vs. shared consumer with tenant filtering — throughput vs. operational simplicity trade-off.
