LLD 09 — Feedback Loop / Role Widget Platform

LLD 09 — Feedback Loop

Feeds usage signals back into three places: new questions join widget corpora, KG edge weights shift toward what people actually use, and repeated unanswered questions become coverage gaps for the reuse ladder.

Plain English

Makes the system smarter over time without any manual curation. Three separate feedback paths run continuously:

  • Path A — Novel question promotion (incremental). When an employee asks something that matches no existing question, it is embedded immediately and added to a cluster. The cluster only promotes to a canonical question when enough distinct users have asked similar things — one person's busy afternoon does not trigger it. When promoted, an LLM writes the canonical text, an entity leak check strips any PII or company-specific numbers, and the question joins the global corpus. It is then routed: attach to an existing widget, raise a gap for LLD 04 to link a cross-bucket widget, or raise a gap for LLD 05 to generate a new one.
  • Path B — Widget feedback (nightly batch). Explicit signals (thumbs up/down, pin, hide) and implicit signals (opened, never opened, dwell time) are logged. Nightly, a batch adjusts knowledge graph edge weights per bucket. A widget consistently hidden in one bucket loses weight for that bucket only — it stays active in others. No interactions for a configurable number of days deprecates the widget and invalidates the cache.
  • Path C — Bucket health (weekly batch). Checks what percentage of each bucket's responsibilities have a widget. Detects employees whose job descriptions have drifted far enough from their bucket that they should be re-matched. Detects buckets that should be split or merged — but presents both as admin decisions; the system never splits or merges automatically.

3 · Components

A — Novel Question Promotion (Incremental)

Novel Question Embedder

Responsibility: Each unmatched question_log row is embedded immediately (not batched) so it is available for cluster assignment without waiting for a nightly job.

Interface: embedNovelQuestion(log_id, query_text) → vector

Reads: question_log (unmatched rows)

Writes: embedding stored in-memory cluster buffer; not persisted to Postgres until cluster promotes

Incremental Cluster Updater

Responsibility: New embedding joins the nearest HDBSCAN cluster as it arrives. A cluster is promoted the moment it crosses the distinct-user threshold — not a raw count. One busy afternoon from one user does not trigger promotion.

Threshold check: distinct_users ≥ NOVEL_QUESTION_CLUSTER_THRESHOLD_DISTINCT_USERS AND similarity above NOVEL_QUESTION_CLUSTER_SIMILARITY_THRESHOLD

Writes on promotion: Triggers canonical question writer; records cluster_id for backfill.

Re-Cluster Job (Occasional)

Responsibility: Tidies cluster boundaries when incremental assignments have drifted. Not the primary promotion path — exists only to correct boundary noise. Runs on a schedule independent of promotion events.

Effect: May re-assign existing promoted questions to adjacent clusters; does not depromote already-active questions.

Canonical Question Writer

Responsibility: For each promoted cluster: check against existing questions (cosine similarity above threshold → add as alias, not a new question). If genuinely new: LLM writes canonical question text + intent. Entity leakage check required before writing to global corpus — promoted questions must be reviewed for PII or client-specific values before promotion.

Writes: questions (new canonical or alias), widget_questions (link), question_log.matched_question_id (backfill)

Routing Decision (post-promotion)

Responsibility: Determines where the newly promoted question goes:

  • Bucket widget answers it → attach via widget_questions.
  • Only a cross-bucket widget answers it → raise gap entry for LLD 4 (link the cross-bucket widget in).
  • Nothing answers it → raise gap entry for LLD 5 (generate a new widget).

Writes: widget_questions and/or bucket_coverage_gaps

Question Embedder + Index Updater

Responsibility: Embeds the new canonical question, upserts into the Redis question index (qidx:bucket via LLD 7), backfills question_log.matched_question_id for all clustered rows, and adds the question to the session transition graph used by LLD 11.

Writes: qidx:bucket upsert (LLD 7), question_log backfill, transition graph update

B — Widget Feedback

POST /api/feedback Handler

Responsibility: Accepts and logs both explicit signals (thumbs up/down, hide, pin) and implicit signals (opened, dwell_time, follow_up_question, never_opened).

Interface: POST /api/feedback {user_id, widget_id, signal, value?} → 202

Writes: widget_events row per signal

Idempotency: Each signal event is a separate append-only row; duplicate submissions from retries are acceptable (aggregation is idempotent).

Daily KG Weight Adjuster

Responsibility: Aggregates widget_events from the past day and converts signals into per-bucket adjustments on SERVED_BY and CONTAINS edge weights in kg_edges.

Deprecation logic: Widget consistently hidden within a specific bucket → weight drifts below inclusion threshold for that bucket only (not globally). Consistently poor signals across all buckets → added to admin review queue. Unused for WIDGET_DEPRECATION_INACTIVITY_DAYS → status flipped to deprecated; bucket version bumped; cache keys invalidated.

Writes: kg_edges (weight updates), widgets.status (deprecation), buckets.version (bump on deprecation)

C — Bucket Health (Weekly)

Coverage Reporter

Responsibility: Computes the share of a bucket's members' tracked responsibilities that are covered by at least one active widget. This is the primary quality metric for a bucket. Results written to bucket_coverage_gaps.

Writes: bucket_coverage_gaps (coverage percentage + gap list)

Drift Detector

Responsibility: Identifies bucket members whose JDs have drifted away from their bucket's profile (embedding distance grown beyond threshold since last assignment). Raises a re-run of LLD 2 (Bucket Matcher) for those users.

Writes: Enqueues BucketMatchJob(user_id) for drifted members

Split/Merge Suggester

Responsibility: Detects when a bucket contains two clear sub-clusters (suggests split) or when two buckets are near-identical (suggests merge). Both are presented as admin decisions — the system never splits or merges buckets automatically.

Writes: Admin notification with evidence; no schema changes until admin confirms

10 · Edge Cases & Open Questions

Edge Cases
  • Single user gaming promotion via repeated novel questions — distinct-user filter prevents; one user's cluster never crosses threshold alone.
  • Entity leakage in promoted questions (employee names, revenue figures in question text) — canonicalization must strip entities; promotion into the global corpus requires a review step before writing.
  • Fork sprawl: every slightly different phrasing treated as new cluster — similarity threshold must be tuned; alias detection is the primary defence.
  • Question that aliases to multiple existing canonical questions — attach as alias to the closest one; log the ambiguity for admin review.
Open Questions
  • What is the right review gate before a promoted question joins the global corpus? (async admin review vs. automated entity-check only)
  • How should the deprecation threshold interact with seasonal widgets (e.g., year-end review widgets inactive for 10 months)?
  • Should implicit signals (dwell time, never opened) carry the same weight as explicit signals (thumbs down) in KG weight adjustment?
