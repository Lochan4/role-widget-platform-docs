LLD 10 — Access Guard

Every path that can surface a widget or its data checks the user's access profile against the widget's access metadata. A user who is not allowed is told so and never sees the widget or its data.

Plain English

The security enforcement layer. Every path that can show a widget or return its data runs through one function: can_access(user_profile, widget_access). There are four check points — bundle build, question routing, widget data API, and before data is passed to the LLM. A denial at any point is consistent and logged.

The function returns one of three outcomes:

  • Allow — the user's access level meets the widget's minimum, and their department matches any restrictions.
  • Scoped — allowed, but data is filtered (e.g. they can see the widget, but only their team's rows, not the whole company's). The scope filter is injected as a mandatory SQL predicate in LLD 08 — never in the UI, where it could be bypassed.
  • Deny — everything else. A widget with no access metadata configured defaults to deny.

Key principle: buckets never grant access. Having a secondary bucket does not expand what data you can see. Your seniority level and department are the only things that matter. Access levels are inferred from the JD, title, grade, and org chart at HR sync time. Every deny is written to an append-only audit log — required for HR data compliance.

3 · Components

Level Inferrer

Responsibility: Infers the user's access level from JD, title, grade, department, and reporting line at HR sync time (LLD 1). Inferred levels fail closed: confidential and restricted widgets require an admin-confirmed level before access is granted.

Interface: inferLevel(user_id, jd_chunks, title, grade, department, manager_chain) → {level: string, confidence: float}

Confidence threshold: Below LEVEL_INFERENCE_CONFIDENCE_THRESHOLD, admin must confirm before the user can access confidential or restricted widgets.

Writes: user_access_profile.level, user_access_profile.confidence

Refresh: Run at every HR sync (LLD 1); also on admin override.

can_access(profile, widget_access) → allow | scoped | deny

Responsibility: The single authoritative function called at all four check points. Pure function — no I/O; takes already-loaded profile and widget_access objects.

Logic:

  • allow: level ≥ min_level (or role in allowed_roles) AND department matches (if dept restriction set)
  • scoped: Allowed by level/dept, but data_scope restricts data visibility (self / team / department / company). Scope is applied as a mandatory SQL filter in LLD 8 — never in the UI. Widget is visible but shows filtered data.
  • deny: Everything else. Widget with no widget_access row → deny by default (DEFAULT_SENSITIVITY = restricted).

Tenant overrides: widget_access.tenant_overrides allows a client admin to expand access for their tenant without touching global metadata.

Access Metadata Cache

Responsibility: Loads and caches widget access metadata and user access profiles so every can_access call is a Redis read, not a Postgres read.

Keys:

  • wacl:{widget_id}:{tenant_id} — hash; pinned; invalidated by any widget_access change
  • uacl:{user_id} — hash; refreshed at HR sync cadence; ACCESS_CACHE_TTL_SECONDS TBD

Note: rag:* cache keys include the access scope to prevent cross-user answer leakage. wdata:* keys include the data_scope segment.

Denied Response Generator

Responsibility: Returns a contextual denial message ("This information is restricted for your role") with no numbers, chart, or data preview. If any alternative widget matched the question at the user's allowed level, offers it.

Interface: buildDeniedResponse(user_id, widget_id, question_text, alternatives: Widget[]) → DeniedResponse

Writes: access_decisions row (decision=deny, reason, ts)

Access Decision Logger

Responsibility: Records every deny and every scoped serve to access_decisions. Repeated denials on the same widget for the same user → surfaces a "request access" flow to the client admin.

Interface: logDecision(user_id, widget_id, decision: 'allow'|'scoped'|'deny', reason, scope?) → void

Writes: access_decisions (append-only)

Audit use: Client can query access_decisions to prove who saw what — required for HR data compliance.

5 · Generated Widgets & Access Metadata

Generated widget invariant
  • LLD 5 (Generator) proposes sensitivity + min_level based on data touched: revenue, salaries, and margin data lean restrictive by default.
  • A reviewer must confirm the proposed access metadata before the widget is published.
  • Until confirmed, the widget is treated as restricted (deny by default at all check points).

10 · Edge Cases & Open Questions

Edge Cases
  • Widget with no widget_access row — denied by default at all check points; widget will not surface to any user until access metadata is confirmed.
  • Level inferred below the user's real level (e.g., employee promoted but HR sync has not run) — widget access denied until next sync; no workaround without admin override.
  • data_scope scoping applied in SQL filter, not UI — widget may appear in the user's bundle and answer their question, but the rows returned are filtered to their scope; they cannot see company-wide figures if their scope is team-only.
  • Tenant overrides in widget_access allow a client admin to expand access for their tenant without touching global metadata — must not allow widening beyond the global sensitivity cap.
  • rag:* cache key includes access scope — prevents user A's scoped answer from being served to user B with different scope even if the question hash matches.
Open Questions
  • Should the "request access" flow (triggered by repeated denials) go directly to the client admin, or pass through a platform approval step first?
  • How should level_inference_confidence be displayed to the admin — a numeric score or a qualitative label?
  • At what cadence should access_decisions be retained before archiving — compliance requirements are client-specific.
