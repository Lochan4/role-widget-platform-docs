LLD 11 — Bucket Learner

Tracks which buckets answer each user's questions, accumulates evidence with time decay, and automatically adds a secondary bucket once a clear pattern emerges — then removes it if the pattern fades.

Plain English

Automatically detects when an employee's actual day-to-day work has outgrown their primary role group and quietly adds a secondary bucket — giving them access to that bucket's widgets on their dashboard.

Every time an employee's question is answered by a widget from a bucket that is not their primary, a signal is recorded. An affinity scorer maintains a time-decaying score per (user, bucket) pair — recent behaviour weighs more than old behaviour. The score only triggers a secondary assignment when it crosses a threshold AND at least a minimum number of distinct questions have contributed AND at least a minimum number of distinct days have contributed. One busy afternoon does not decide anything.

The lifecycle has six states: candidate → inferred secondary → confirmed → expired, with admin blocked as a circuit breaker. Hysteresis prevents flickering — the removal threshold is lower than the add threshold, so a secondary bucket will not be removed just because signals temporarily drop.

When the same secondary bucket appears as a pattern across many members of one primary bucket, that is a structural signal — LLD 04 (Reuse Ladder) is notified to link the most-used widgets from the secondary directly into the primary, resolving the pattern for the whole bucket rather than each individual.

3 · Components

Question Signal Recorder

Responsibility: For every routed question answered by a widget outside the user's primary bucket, record evidence for each bucket the matched widget belongs to. Denied matches count too — they signal what the user is trying to find even if access blocks them.

Interface: recordSignal(user_id, widget_id, widget_buckets, in_primary, denied) → void

Writes: user_bucket_affinity pending-update buffer (debounced before Postgres write)

Note: Whether denied signals should count toward promotion is an open question — see section 10.

Affinity Scorer (per-event with time decay)

Responsibility: Updates user_bucket_affinity.score on each recorded event. Recent behaviour weighs more than old behaviour. One busy afternoon from one user does not decide anything — both distinct-question and distinct-day guards must be met before promotion.

Score formula: score = decayed_previous × AFFINITY_TIME_DECAY_HALF_LIFE_DAYS + event_weight × recency_multiplier

Writes: user_bucket_affinity.score, user_bucket_affinity.last_event_ts, user_bucket_affinity.distinct_question_count, user_bucket_affinity.distinct_day_count

ponytail: half-life decay is a scalar; upgrade to per-signal-type weights if signal heterogeneity grows.

Decision Evaluator (per-event, debounced per user)

Responsibility: Evaluates whether to add or remove a secondary bucket after each affinity update. Uses hysteresis (add_threshold > remove_threshold) to prevent flickering — a bucket assigned as secondary won't be removed until the score drops meaningfully below the add threshold.

Add condition: score ≥ AFFINITY_ADD_THRESHOLD AND distinct_questions ≥ AFFINITY_MIN_DISTINCT_QUESTIONS AND distinct_days ≥ AFFINITY_MIN_DISTINCT_DAYS

Remove condition: score < AFFINITY_REMOVE_THRESHOLD (and status is inferred_secondary, not confirmed)

Debounce: AFFINITY_DEBOUNCE_MS TBD — multiple rapid signals per user collapse to one evaluation.

Lifecycle State Machine Driver

Responsibility: Executes lifecycle transitions (candidate → inferred_secondary → confirmed → expired → admin_blocked) and writes each transition to bucket_assignment_decisions with evidence.

Writes: user_bucket_map (add/remove secondary row), bucket_assignment_decisions (append-only audit), user_bucket_affinity.status

Explainability: Every transition records the current score and evidence_question_ids. Admin can read: "Added after 9 procurement questions over 3 weeks."

Admin Notifier

Responsibility: Emits a notification when a bucket transitions to inferred_secondary. Admin can reverse — sets status = expired and sets an admin_blocked flag that prevents re-inference until the admin lifts it.

Interface: notifyAdmin(tenant_id, user_id, bucket_id, evidence_summary) → void

Writes: Admin notification queue; user_bucket_affinity.admin_blocked (if reversed)

Bundle Rebuild Trigger

Responsibility: Each status change (inferred_secondary added, expired) triggers a BundleBuildJob for the affected user (LLD 3) and a cache update (LLD 7). The rebuild picks up the new secondary bucket's widgets automatically.

Interface: triggerBundleRebuild(user_id) → void

Effect on routing: After rebuild, LLD 6 searches primary first, then inferred + confirmed secondaries, then the global library.

Bucket-Level Gap Detector

Responsibility: When many members of one primary bucket gain the same inferred secondary bucket, raise a bucket_coverage_gaps entry for LLD 4. LLD 4 will typically link the most-used widgets from the secondary into the primary to resolve the pattern structurally.

Threshold: BUCKET_LEVEL_GAP_MIN_MEMBERS TBD

Writes: bucket_coverage_gaps row tagged with both primary and secondary bucket IDs

4 · Bucket Affinity Lifecycle State Machine

stateDiagram-v2 [*] --> candidate: first signal recorded outside primary bucket candidate --> inferred_secondary: score ≥ add_threshold AND min_distinct_questions AND min_distinct_days inferred_secondary --> confirmed: admin or user confirms inferred_secondary --> expired: score decays below remove_threshold confirmed --> expired: admin removes (confirmed buckets don't expire on their own) expired --> candidate: new signals accumulate (if not admin_blocked) expired --> admin_blocked: admin reverses an inferred_secondary admin_blocked --> candidate: admin lifts block

Stored in user_bucket_affinity.status. confirmed status does not expire on its own — only admin removal moves it to expired. admin_blocked prevents re-inference until the admin explicitly lifts the block.

5 · Effect on the User

Routing order after inferred_secondary added: primary bucket → inferred + confirmed secondaries → global widget library.

Dashboard: A section appears with the secondary bucket's most-used widgets, filtered by the access guard. The section label explains why it appeared ("You often ask procurement questions").

Each status change: Triggers a bundle rebuild so the next request picks up the change without a manual refresh.

6 · Redis Keys

LLD 11 does not own any Redis keys directly. Status changes trigger BundleBuildJob (LLD 3) which writes bundle:{user_id} via LLD 7.

10 · Edge Cases & Open Questions

Edge Cases
  • Admin blocks re-inference after reversal — user's affinity score for that bucket can still accumulate, but will never trigger inferred_secondary again until the admin lifts the block. Score is not cleared.
  • User changes primary bucket (LLD 2 re-runs) — all inferred_secondary and candidate affinity scores are retained; the new primary is checked against existing secondaries to avoid circular assignment.
  • Widget belongs to three buckets — evidence is credited to all three simultaneously; the most-evidenced bucket promotes first.
  • Score oscillates around remove_threshold — hysteresis gap between add and remove thresholds is the primary defence; gap must be wide enough to absorb weekly usage variance.
Open Questions
  • Should inferred secondary buckets appear on the user's dashboard immediately (at inferred_secondary) or only after admin or user confirmation (confirmed)?
  • Should denied-match signals count as affinity evidence? A user denied access to a widget repeatedly may be signalling need — but their access level was checked and rejected. Counting these could make the access guard feel like it is working against itself.
  • Cold start: a new bucket has no question-sequence data in the transition graph. Should LLD 11 fall back to nearest-bucket transitions until enough sessions accumulate, or simply require a minimum session count before activating?
